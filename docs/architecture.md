# Foundation architecture

Foreman runs one local Node service. A durable JSON state file holds projects, tasks, runs, role configuration, assignments, guidance, validation, review, approval, and append-only event records. Each mutation is serialized and atomically renamed into place. The React UI reads that persisted state and receives events over SSE. UHP and Hindsight are adapters at the service boundary; neither owns Foreman's project identity or canonical Git truth.

## Control flow

1. The operator creates a persistent project, task, and run, then speaks to the Planner. The Planner is the only primary chat surface.
2. The Planner and Orchestrator use separate UHP session chains. Foreman records each response and session ID so a session may continue or rotate without replacing the project. A rotation changes the UHP conversation identity; project memory and Git promotion state remain attached to the project.
3. The Orchestrator proposes bounded Worker assignments. Foreman validates the requested harness/model against live discovery, persists the submission intent and idempotency key, then sends UHP work. Workers are inspectable but are not direct operator chat targets.
4. New operator guidance is assigned a monotonic sequence. While a Worker is active, it waits in the durable queue. At a defined checkpoint, the Orchestrator acknowledges whether it applied the guidance, needs to replan, or is waiting. Invalidated Worker work is cancelled and revised explicitly.
5. A Reviewer independently examines proposed changes and evidence. Foreman must independently verify the exact Git result and configured validation before a human approval can accept changes. A Reviewer response or human approval alone cannot mutate canonical Git state. Approval and Git promotion are distinct persisted states.

## Authority and failure behavior

Agent prose is evidence or a proposal, not a state transition by itself. Git commits, exact workspace snapshots, and controller-observed checks are authoritative for code acceptance. Hindsight recall is bounded and advisory. If Hindsight is unavailable, memory status degrades visibly while ordinary run state and validation remain available. Usage is represented as measured only when reported by UHP; missing token, cost, or quota fields remain unavailable.

The external host CLI bridge remains outside Foreman core. Foreman persists its Worker response provenance and complete snapshot, verifies the snapshot and scope against the pinned base, computes an exact diff, then runs configured validation commands in a disposable workspace derived from that base. Recorded live Worker evidence can be imported and reverified locally without starting another Worker task; this receives its own `recorded_live_import` provenance distinct from deterministic `recorded_replay`. The Reviewer receives the diff and controller-observed checks in a fresh context without the Worker checkout. Claude runs with an empty tool allowlist; Codex runs with `--sandbox read-only`, which may still expose read-only shell tools. The single live Reviewer response in [the recorded evidence](../investigations/local-cli-uhp/evidence/actual-reviewer-smoke.json) recommended the change and recorded a proven Claude read-only boundary; the run was `awaiting_approval` with acceptance `not_decided` when that evidence was captured. The operator later approved it in the UI; the [separate approval record](../investigations/local-cli-uhp/evidence/actual-reviewer-approval.json) records the human decision and pinned input base; the smoke run has not been promoted and has no result commit. Its validation policy contained one README SHA-256 check, which verifies recorded bytes but is not a broader project test suite. Foreman records recommendations independently; they cannot change the verified diff or mark it accepted, and Foreman does not apply Reviewer changes. Human approval is a separate decision transition, gated on verified snapshot/scope and configured validation policy; Git promotion remains explicit and later.


## Approval and Git promotion

Human approval records an immutable decision bound to the evidence digest and pinned input base. Its `evidenceCommit` names the pinned base; it is not the result commit. Promotion is a separate explicit operation. Before creating a result commit, the controller rechecks the stored snapshot bytes and modes, allowed scope, pinned base, validation record, and Reviewer binding. It builds the tree in an isolated worktree, commits with the pinned base as parent, then compares the complete result tree to the approved snapshot. Only that verified result commit and tree are reported as applied. A failed or interrupted attempt remains distinct from the human decision and can be retried idempotently; conflicting branch state is rejected.
